Set up the current project to use the Kendo Design System. This is the `init` flow of the `kendo-design` skill — a thin orchestrator that generates a tailored `DESIGN.md` at the project root.

## Also load the themes skill

You are already running as the `kendo-design` skill, so you own the DESIGN.md structure, principles, and token reference. To detect the project's theme and resolve token values, also load the **`kendo-themes` skill** (theme packages, CSS custom properties, and per-theme values for meridian, bootstrap, material, fluent, default, classic).

Do not proceed until `kendo-themes` is loaded.

## Step 1: Scan the project

Crawl the codebase to decide which mode applies:

- Read `package.json` for `@progress/kendo-theme-*` packages and any UI framework (React, Angular, Vue, Blazor, jQuery).
- Look for existing design tokens: CSS custom properties (`--kendo-*`, `--color-*`), Tailwind config, SCSS variables, or a theme import.
- Look for an existing project-root `DESIGN.md`. If one exists, STOP and ask whether to refresh, merge, or skip — never overwrite silently.
- Note the rendered styling approach (Kendo theme CSS, Tailwind, plain CSS, CSS-in-JS).

Report briefly what you found before choosing a mode.

## Step 2: Pick a mode

**Scan mode** — the project already has styling (a Kendo theme package, existing tokens, or committed brand colors):
- Detect which theme is in use from `package.json` (e.g. `@progress/kendo-theme-meridian` → meridian). If none is installed but the project clearly uses Kendo/Telerik components, ask which theme they intend.
- Generate a `DESIGN.md` seeded from the matching bundled theme spec (`themes/<theme>/DESIGN.md`, e.g. `themes/meridian/DESIGN.md`), then reconcile it with what the project actually uses: keep the project's real brand colors, font family, and spacing choices where they diverge from defaults. The project's committed values win — identity preservation matters.
- If the detected theme is a bundled placeholder (`bootstrap`, `material`, `fluent`, `classic` — not yet authored), fall back to `themes/meridian/DESIGN.md` as the base and note the substitution.
- Where the project is silent, fall back to the chosen theme's token values (from the `kendo-themes` skill).

**Seed mode** — the project is pre-implementation (empty, or no styling committed yet):
- Ask which theme should anchor the system: **meridian** (recommended default), bootstrap, material, fluent, default, or classic.
- Ask a few short questions only where they change the output: primary brand color (or keep the theme default), preferred font family (or keep default), and enforcement strictness (strict = flag all on-grid deviations; relaxed = flag only principle violations).
- Write a starter `DESIGN.md` from the matching bundled theme spec (`themes/<theme>/DESIGN.md`, defaulting to `themes/meridian/DESIGN.md`) with those answers applied. Mark it with a comment so it's clear it's a starting point: `<!-- Seeded by /kendo-design init. Customize freely — this file takes precedence over the plugin's bundled spec. -->`

Decide by scanning first. If the scan finds no tokens, no theme package, and no committed colors, offer seed mode — don't switch silently.

## Step 3: Write DESIGN.md

- Write to `./DESIGN.md` at the project root.
- Follow the section order and token schema defined by the bundled theme spec (`themes/<theme>/DESIGN.md`, e.g. `themes/meridian/DESIGN.md`) — do not invent new top-level sections.
- Add a header comment noting the file was generated by `/kendo-design init` and takes precedence over the bundled spec (per the skill's precedence rules).
- Keep it tailored: every token and rule should reflect either the project's real usage (scan mode) or the user's confirmed choices (seed mode). Do not dump the raw bundled spec unchanged.

## Step 4: Wrap up

Summarize tersely:
- Which mode ran and why
- Which theme anchors the system
- What was written, and which values were tailored (brand color, font, strictness)
- That the project-local `DESIGN.md` now takes precedence over the plugin default

Then point the user at the next useful command — `/kendo-design audit` to check the current code against the new spec, `/kendo-design modernize` to align it, or `/kendo-design generate` to build new UI on top of it.
